서버 터졌다는 말, 물류센터로 풀기

서비스가 왜 느려지고 왜 멈추는지, 그 말들을 알아듣게 돼요.

전체 흐름

  1. 요청 — 내가 버튼을 누르면 요청 하나가 출발해요
  2. 트래픽 — 그 요청이 한꺼번에 몰려요
  3. 로드밸런서 — 입구에서 여유 있는 서버로 나눠 줘요
  4. 서버 — 받은 요청을 처리해서 결과를 돌려줘요
  5. 캐시 — 자주 나가는 답은 미리 꺼내 둬요
  6. 스케일 아웃 — 그래도 모자라면 서버를 더 띄워요
  7. 배포 — 새 버전을 실제 서비스에 올려요
  8. 다운타임 — 그 사이 멈춰 있던 시간이 남아요

1. 서버

한 줄로 · 주문 오면 물건 꺼내서 보내주는 물류센터
실제로는

요청을 받아서 처리하고 답을 돌려주는 컴퓨터예요. 내 폰이나 노트북은 요청을 보내는 쪽이고, 서버는 그걸 받아 주는 쪽이죠. 한 대가 수천 명의 요청을 동시에 받다가 한계를 넘으면 느려지거나 아예 답을 못 하는데, 그 상태를 두고 '터졌다'고 불러요.

이렇게 작동해요
  1. 내가 앱에서 버튼을 누른다
  2. 요청이 인터넷을 타고 서버까지 간다
  3. 서버가 필요한 데이터를 꺼내 처리한다
  4. 결과를 답으로 돌려보낸다
  5. 내 화면에 뜬다
AI 쓸 때 여기서 만나요

챗GPT나 클로드에 질문을 넣었을 때 답은 내 컴퓨터가 아니라 저쪽 서버가 만들어요. 그래서 몰리는 시간대엔 "지금 사용량이 많습니다" 같은 안내가 뜨죠.

예를 들면

클로드에 "이 메일 다듬어 줘"라고 치면, 내 노트북은 그 문장을 보내고 기다리기만 해요. 다듬는 계산은 전부 저쪽 서버에서 돌아가거든요. 그러니 내 컴퓨터가 멀쩡해도 서버가 바쁘면 답이 늦어요.

써먹는 요령

답이 안 나오는데 내 와이파이는 정상이면, 대개 내 문제가 아니라 저쪽이 바쁜 거예요. 상태 페이지를 먼저 확인하면 괜히 재설치하는 헛수고를 안 해요.

✓

해보기 · 서비스 상태 페이지 열어 두기

앤트로픽은 서비스가 정상인지 알려주는 페이지를 따로 운영해요. 북마크해 두면 다음에 안 될 때 1분 컷으로 확인해요.

status.anthropic.com

2. 트래픽

한 줄로 · 그 센터로 오늘 쏟아지는 상자 백만 개
실제로는

서버로 들어오는 요청의 양이에요. 접속한 사람 수가 아니라 요청 건수로 세고, 보통 초당 몇 건인지로 따져요. 들어오는 양이 처리 능력을 넘기면 대기줄이 생기면서 응답이 느려져요.

이렇게 작동해요
  1. 사람들이 동시에 화면을 열고 버튼을 누른다
  2. 요청이 한꺼번에 서버로 몰린다
  3. 서버가 처리할 수 있는 만큼만 받아 처리한다
  4. 넘치는 요청은 줄을 서거나 거절당한다
  5. 화면에는 느려짐이나 에러로 나타난다
AI 쓸 때 여기서 만나요

AI를 API로 쓰기 시작하면 "분당 요청 수 제한"이라는 말을 만나요. 내가 보낼 수 있는 트래픽의 상한선이거든요.

예를 들면

웹페이지 하나를 열면 요청은 한 개가 아니에요. 글씨, 그림, 글꼴, 데이터까지 따로따로 가서 수십 개가 되죠. 사람 1명이 들어와도 상자는 수십 개가 쏟아지는 셈이에요.

써먹는 요령

AI에 자동으로 질문을 쏘는 스크립트를 만들 때는 사이에 쉬는 시간을 꼭 넣어요. 한꺼번에 몰아 보내면 제한에 걸려 중간에 다 막혀요.

✓

해보기 · 요청 개수 눈으로 보기

브라우저 개발자 도구를 켜고 새로고침하면 요청이 하나씩 쌓이는 게 보여요. 아래에 총 개수도 나와요.

윈도우: F12 → Network 탭 → 새로고침 / 맥: Cmd+Option+I → Network 탭 → 새로고침

3. 로드밸런서

한 줄로 · 입구에 선 반장이 상자를 빈 컨베이어로 쪽쪽 나눠 주는 일
실제로는

들어온 요청을 여러 서버에 나눠 보내는 역할이에요. 사용자는 주소 하나만 알면 되고, 그 뒤에 서버가 몇 대 있는지는 몰라도 되죠. 답이 없는 서버는 명단에서 빼 버리니까, 한 대가 죽어도 서비스는 계속 돌아가요.

이렇게 작동해요
  1. 요청이 먼저 로드밸런서에 도착한다
  2. 지금 여유 있는 서버를 하나 고른다
  3. 그 서버에 요청을 넘긴다
  4. 결과를 받아 사용자에게 돌려준다
  5. 응답 없는 서버는 명단에서 빼 둔다
AI 쓸 때 여기서 만나요

Cursor나 Claude Code로 서비스를 만들다가 "사람이 몰리면 어떻게 버티죠?" 하고 물으면 거의 이 얘기가 나와요. 클라우드에 올릴 때 설정 항목으로도 마주쳐요.

예를 들면

서버 3대에 요청 90만 건이 오면 한 대당 30만 건씩 가요. 그중 1대가 꺼지면 남은 2대가 45만 건씩 받고요. 사용자는 서버가 하나 죽은 걸 눈치채지 못해요.

써먹는 요령

서버를 늘릴 생각이라면 이 나눠 주는 장치를 먼저 둬야 해요. 안 두면 주소가 여러 개로 갈려서 사용자가 어디로 가야 할지 몰라요.

✓

해보기 · AI에 나누는 방식 물어보기

요청을 어떤 기준으로 나누는지 몇 가지 방식이 있어요. 비유로 설명해 달라고 하면 한 번에 들어와요.

로드밸런서가 요청을 여러 서버에 나누는 방식에 어떤 게 있는지, 코딩 모르는 사람 기준으로 비유를 써서 알려줘.

4. 스케일 아웃

한 줄로 · 넘치면 똑같은 센터를 옆에 하나 더 짓는 것
실제로는

서버 대수를 늘려서 처리 능력을 키우는 방법이에요. 한 대를 더 좋은 사양으로 갈아 끼우는 쪽은 스케일 업이라 부르고, 똑같은 걸 여러 대로 늘리는 쪽이 스케일 아웃이죠. 대수를 늘렸으면 요청을 나눠 줄 로드밸런서가 같이 있어야 해요.

이렇게 작동해요
  1. 트래픽이 한 대로 버틸 한계에 가까워진다
  2. 똑같은 서버를 한 대 더 띄운다
  3. 로드밸런서 명단에 새 서버를 올린다
  4. 요청이 두 대로 나뉘어 들어간다
  5. 한가해지면 다시 한 대로 줄인다
AI 쓸 때 여기서 만나요

클라우드 요금이 쓴 만큼 늘고 줄는 이유가 여기 있어요. AI에 "사람 몰릴 때 대비하려면?"이라고 물으면 자동으로 대수를 늘리는 설정을 권해요.

예를 들면

서버 1대가 초당 500건을 처리하는데 2,000건이 들어오면 4대로 늘려요. 밤에 200건으로 떨어지면 1대만 남겨 요금을 아끼죠. 센터를 짓고 허무는 게 클릭 몇 번이라 이게 가능해요.

써먹는 요령

처음부터 크게 지을 필요는 없어요. 작게 띄워 놓고 몰릴 때만 늘리는 쪽이 돈이 훨씬 덜 들어요.

✓

해보기 · 두 방식 비교표 받기

서버를 늘릴지 키울지는 상황마다 달라요. AI에 표로 정리해 달라고 하면 판단 기준이 잡혀요.

스케일 업과 스케일 아웃을 각각 언제 쓰는지, 장단점을 표로 정리해 줘. 예시도 하나씩 붙여 줘.

5. 캐시

한 줄로 · 제일 많이 나가는 물건을 문 앞에 미리 쌓아 두는 자리
실제로는

한 번 만든 결과를 가까운 곳에 저장해 두고, 다음엔 그대로 꺼내 쓰는 거예요. 매번 처음부터 계산하거나 찾아오지 않으니 훨씬 빠르죠. 대신 원본이 바뀌었는데 옛 결과를 보여줄 수 있어서, 보관 기간을 정해 두고 지나면 버려요.

이렇게 작동해요
  1. 처음 요청이 오면 원래대로 계산해서 답을 만든다
  2. 그 답을 복사해 가까운 곳에 저장한다
  3. 같은 요청이 또 오면 저장해 둔 걸 바로 준다
  4. 보관 기간이 지나면 저장해 둔 걸 버린다
  5. 다음 요청은 다시 새로 계산한다
AI 쓸 때 여기서 만나요

긴 문서를 붙여 놓고 질문을 계속 이어갈 때, 그 앞부분을 저장해 두고 재사용하는 기능이 클로드 API에 있어요. 같은 걸 매번 다시 읽히지 않으니 응답이 빨라지고 비용도 내려가요.

예를 들면

사내 규정 50쪽을 붙여 두고 질문을 열 번 하면, 원래는 매번 50쪽을 처음부터 다시 읽어요. 저장해 두고 쓰면 그 50쪽은 한 번만 읽고 질문만 새로 보는 셈이죠. 그래서 두 번째 답부터 체감이 확 달라요.

써먹는 요령

화면이 옛 내용으로 멈춰 있으면 저장된 걸 보고 있을 때가 많아요. 그럴 땐 그냥 새로고침이 아니라 강력 새로고침으로 다시 받아 오면 돼요.

✓

해보기 · 강력 새로고침 해 보기

브라우저가 저장해 둔 화면을 무시하고 새로 받아 와요. 수정했는데 화면이 그대로일 때 제일 먼저 써 볼 손동작이에요.

윈도우: Ctrl+Shift+R / 맥: Cmd+Shift+R

6. 배포

한 줄로 · 새 분류기를 들여와 오늘부터 진짜로 돌리는 그 순간
실제로는

다 만든 코드를 실제 사용자가 쓰는 서버에 올려서, 지금부터 그게 돌게 하는 일이에요. 내 컴퓨터에서 잘 되던 게 올리면 안 되는 일이 흔해서, 올리기 전에 테스트를 돌려 봐요. 문제가 터지면 곧장 이전 버전으로 되돌릴 수 있게 해 두는 게 기본이고요.

이렇게 작동해요
  1. 코드를 고치고 내 컴퓨터에서 확인한다
  2. 테스트를 돌려 깨진 데가 없는지 본다
  3. 실제 서버에 새 버전을 올린다
  4. 요청을 새 버전으로 넘긴다
  5. 이상하면 이전 버전으로 되돌린다
AI 쓸 때 여기서 만나요

Claude Code나 Cursor로 웹페이지를 만들면 마지막에 "배포하세요"라는 안내가 나와요. 그 단계를 안 하면 내 컴퓨터에서만 보이고 남에게 링크를 줄 수가 없어요.

예를 들면

AI가 만들어 준 페이지를 내 컴퓨터에서 열면 주소가 localhost로 시작해요. 그 주소는 나만 열려요. 남이 볼 수 있는 주소가 생기는 순간이 배포예요.

써먹는 요령

작게 자주 올리는 쪽이 안전해요. 한꺼번에 많이 바꿔 올리면 뭐 때문에 깨졌는지 찾느라 더 오래 걸려요.

✓

해보기 · 배포 순서 받아 적기

AI에 내 수준에 맞춘 순서를 받아 두면 다음에 헤매지 않아요. 무료로 올릴 수 있는 곳까지 같이 물어봐요.

내가 만든 웹페이지를 남이 링크로 볼 수 있게 올리려면 뭘 해야 하는지, 코딩 모르는 사람 기준으로 순서대로 알려줘. 무료로 올릴 수 있는 곳도 같이 추천해 줘.

7. 다운타임

한 줄로 · 기계 바꾸는 동안 센터가 멈춰 있던 시간
실제로는

서비스가 멈춰서 아무도 못 쓰는 시간이에요. 장애로 생기기도 하고, 점검이나 새 버전 올리는 작업 때문에 생기기도 하죠. 요즘은 새 버전을 먼저 띄워 놓고 요청만 옮기는 식으로 멈춤을 거의 없게 만들어요.

이렇게 작동해요
  1. 새 버전 서버를 옆에 먼저 띄운다
  2. 제대로 뜨는지 확인한다
  3. 요청을 새 버전 쪽으로 옮긴다
  4. 옛 버전을 내린다
  5. 사용자는 멈춤을 느끼지 못한다
AI 쓸 때 여기서 만나요

AI 서비스가 안 될 때 상태 페이지에 남는 장애 기록이 바로 이 시간이에요. "새벽 점검 안내" 공지도 멈출 시간을 미리 알려주는 거죠.

예를 들면

"가동률 99.9%"라고 적혀 있으면 한 달에 약 43분은 멈출 수 있다는 뜻이에요. 한 달이 43,200분이고 그중 0.1%니까요. 숫자가 99%로 내려가면 멈추는 시간은 7시간 넘게 늘어나요.

써먹는 요령

마감 직전에 새 버전을 올리지 않아요. 되돌릴 시간이 없는 때에 올리는 게 사고를 키워요.

✓

해보기 · 가동률을 분으로 바꿔 보기

퍼센트로만 보면 감이 안 와요. 분으로 바꿔 보면 그 숫자가 얼마나 센 약속인지 바로 와요.

가동률 99%, 99.9%, 99.99%가 한 달에 각각 몇 분 멈추는 건지 계산해서 표로 보여 줘.
