서버 터졌다, 물류센터로 풀기

"서버 터졌다" 같은 말이 들렸을 때, 지금 어디서 무슨 일이 생긴 건지 그려져요.

1. 서버

비유로 치면 · 주문 오면 물건 꺼내서 보내주는 물류센터
실제로는

서버는 남의 컴퓨터 부탁을 받아 처리하고 결과를 돌려주는 컴퓨터예요. 24시간 켜져 있고 인터넷에 붙어 있죠. 내 폰이나 노트북은 부탁하는 쪽, 서버는 받아서 일하는 쪽입니다.

이렇게 작동해요
  1. 내 폰 앱에서 버튼을 누른다
  2. 인터넷을 타고 요청이 서버에 도착한다
  3. 서버가 데이터를 찾아 처리한다
  4. 결과를 내 폰으로 돌려보낸다
  5. 화면에 내용이 뜬다
AI 쓸 때 여기서 만나요

챗GPT나 클로드에 문장을 보내면 내 노트북이 아니라 그 회사 서버에서 답이 만들어져요. Claude Code로 작업할 때도 코드 파일은 내 컴퓨터에 있지만, 답은 매번 서버를 다녀옵니다.

예를 들면

인터넷은 멀쩡한데 챗GPT만 "문제가 생겼어요"라고 뜨는 날이 있잖아요. 그건 내 쪽이 아니라 저쪽 서버가 힘들어하는 거예요. 반대로 와이파이가 끊기면 요청이 서버까지 가지도 못해서 "연결 안 됨"이 뜨죠.

2. 트래픽

비유로 치면 · 그 센터로 오늘 상자가 백만 개 쏟아진다
실제로는

트래픽은 정해진 시간 동안 서버로 오고 가는 요청과 데이터의 양이에요. 접속한 사람 수, 보낸 요청 수, 주고받은 데이터 크기로 셉니다. 양이 서버가 소화할 수 있는 선을 넘으면 느려지거나 오류가 나죠.

이렇게 작동해요
  1. 사람들이 한꺼번에 접속한다
  2. 요청이 서버로 몰린다
  3. 처리할 수 있는 양을 넘으면 대기줄이 생긴다
  4. 응답이 늦어지거나 오류가 돌아온다
  5. 사람이 빠지면 다시 빨라진다
AI 쓸 때 여기서 만나요

새 모델이 공개된 날 들어가면 답이 뚝뚝 끊기거나 "지금 사용량이 많습니다" 안내가 뜨는데, 그게 트래픽이 몰린 상황이에요.

예를 들면

평소엔 3초면 나오던 답이 공개 당일엔 한참 돌다가 나와요. 글자가 한 자씩 느리게 찍히는 것도 같은 이유고요. 밤늦게 다시 해보면 멀쩡하게 빨라진 걸 느낄 수 있어요.

급한 일은 사람 몰리는 시간을 피하세요. 새 기능 공개 직후, 평일 낮이 제일 붐빕니다.

3. 로드밸런서

비유로 치면 · 입구에 선 반장이 상자를 빈 컨베이어로 나눠준다
실제로는

로드밸런서는 들어오는 요청을 여러 대의 서버에 나눠 보내는 장치예요. 한 대에 몰리지 않게 돌려주고, 죽은 서버는 건너뜁니다. 쓰는 사람 눈에는 주소 하나로 보이지만 뒤에는 서버가 여러 대 있어요.

이렇게 작동해요
  1. 요청이 먼저 로드밸런서에 도착한다
  2. 어느 서버가 여유 있는지 살핀다
  3. 여유 있는 서버로 요청을 넘긴다
  4. 그 서버가 처리해 결과를 만든다
  5. 응답이 나에게 돌아온다
AI 쓸 때 여기서 만나요

AI 서비스는 주소 하나로 들어가지만 뒤에 서버가 수없이 많아요. 내가 직접 만질 일은 없는데, 어쩌다 한 번 오류가 났다가 다시 보내면 되는 이유가 여기 있죠.

예를 들면

같은 질문을 두 번 보냈는데 한 번은 바로, 한 번은 한참 걸릴 때가 있어요. 받아준 서버가 달랐을 수 있거든요. 그래서 한 번 실패한 요청이 재시도에선 그냥 되는 일이 흔합니다.

써먹는 요령

이따금 나는 오류는 바로 포기하지 말고 한 번 더 보내 보세요. 계속 같은 오류가 반복될 때만 다른 원인을 찾으면 됩니다.

4. 스케일 아웃

비유로 치면 · 넘치면 똑같은 센터를 옆에 하나 더 짓는다
실제로는

스케일 아웃은 서버 대수를 늘려서 처리할 수 있는 양을 키우는 방식이에요. 한 대의 성능만 올리는 건 스케일 업이라 부르고요. 요즘 서비스는 사람이 몰리면 자동으로 서버를 늘리고, 한가해지면 줄입니다.

이렇게 작동해요
  1. 트래픽이 늘어난 걸 감지한다
  2. 같은 역할을 하는 서버를 새로 띄운다
  3. 로드밸런서 목록에 새 서버를 넣는다
  4. 요청이 여러 대로 나뉘어 들어간다
  5. 한가해지면 서버를 다시 줄인다
AI 쓸 때 여기서 만나요

AI로 서비스를 만들다가 "사람이 갑자기 몰리면 어떻게 버티죠?" 물으면 이 말이 나와요. 클라우드를 쓰면 설정 몇 줄로 자동으로 늘고 줄게 할 수 있습니다.

예를 들면

티켓 판매처가 오픈 시간 전에 서버를 미리 늘려두는 게 이거예요. 반대로 새벽엔 줄여놓죠. 빌린 만큼 돈을 내니까 줄이는 쪽도 중요하거든요.

5. 캐시

비유로 치면 · 제일 많이 나가는 물건은 문 앞에 미리 쌓아둔다
실제로는

캐시는 자주 쓰는 결과를 가까운 곳에 잠깐 저장해 두고 다시 꺼내 쓰는 방식이에요. 매번 처음부터 찾거나 계산하지 않으니 훨씬 빠르죠. 대신 원본이 바뀌었는데 저장된 옛 내용이 남아 엉뚱한 걸 보여줄 수 있어요.

이렇게 작동해요
  1. 요청이 들어온다
  2. 저장해 둔 게 있나 먼저 본다
  3. 있으면 그걸 바로 내준다
  4. 없으면 원본에서 가져와 처리한다
  5. 그 결과를 저장해 두고 내준다
AI 쓸 때 여기서 만나요

AI한테 웹페이지를 고쳐 달라고 해서 파일은 분명히 바뀌었는데, 브라우저 화면은 그대로인 순간이 있어요. 브라우저가 예전 화면을 들고 있어서 그렇습니다.

예를 들면

버튼 색을 빨강으로 바꿨는데 새로고침해도 파랑이에요. 코드를 열어보면 빨강으로 되어 있죠. 강력 새로고침 한 번에 빨강으로 바뀌는 걸 보면 범인이 캐시였다는 걸 알게 됩니다.

6. 배포

비유로 치면 · 새 분류기를 들여와 오늘부터 진짜로 돌린다
실제로는

배포는 만든 코드를 실제 사용자가 쓰는 서버에 올려서 돌아가게 하는 일이에요. 내 컴퓨터에서 잘 되는 것과 배포는 다른 단계입니다. 배포를 해야 비로소 남들이 그 주소로 들어와 쓸 수 있어요.

이렇게 작동해요
  1. 코드를 고친다
  2. 내 컴퓨터에서 돌려 확인한다
  3. 저장소에 올린다
  4. 자동 검사와 빌드를 통과한다
  5. 실제 서버에 올라가 새 버전이 돌아간다
AI 쓸 때 여기서 만나요

Claude Code나 커서로 만든 페이지를 친구에게 보여주려는 순간 이 말을 만나요. 터미널에 뜬 localhost 주소는 내 컴퓨터 안에서만 열리는 주소라서, 그대로 보내면 친구 쪽에선 안 열립니다.

예를 들면

"다 만들었어!" 하고 localhost:3000을 카톡으로 보냈는데 친구는 빈 화면만 봐요. 또 하나 흔한 장면은 내 컴퓨터에선 멀쩡한데 올리고 나니 깨지는 경우고요. 설정이나 비밀 키가 서버 쪽에 빠져 있을 때 그렇습니다.

써먹는 요령

조금 고치고 바로 올리는 쪽이 안전해요. 한꺼번에 많이 바꿔 올리면 무엇 때문에 깨졌는지 찾기가 어려워집니다.

해보기 · 내 걸 남한테 보여주는 길 알아보기

아래 문장을 그대로 붙여 보세요. 선택지를 비교해 주면 뭘 고를지 정하기 쉬워집니다.

지금 제 컴퓨터에서만 열리는 웹페이지를 다른 사람도 볼 수 있게 올리려면 어떤 방법이 있나요? 코딩을 모르는 사람 기준으로, 방법마다 장단점만 짧게 비교해 주세요.

7. 다운타임

비유로 치면 · 기계 바꾸는 동안 센터는 멈춰 있다
실제로는

다운타임은 서비스가 멈춰서 쓸 수 없는 시간이에요. 미리 알리고 하는 점검도, 갑작스러운 사고도 다 여기에 들어갑니다. 올리는 방식을 잘 짜면 멈추는 시간 없이 새 버전으로 갈아탈 수도 있어요.

이렇게 작동해요
  1. 점검을 시작하거나 사고가 난다
  2. 요청이 처리되지 않고 오류가 돌아온다
  3. 상태 페이지나 공지에 안내가 뜬다
  4. 복구 작업을 한다
  5. 정상으로 돌아온다
AI 쓸 때 여기서 만나요

한창 작업하는데 "잠시 후 다시 시도해 주세요"만 반복되고, 상태 페이지에 장애 기록이 올라와 있으면 그게 다운타임이에요.

예를 들면

보고서를 AI랑 쓰다가 20분쯤 아무 답도 못 받는 날이 있어요. 그동안 대화창에 적어둔 맥락이 날아갈까 조마조마하죠. 복구되고 나면 대화는 보통 그대로 있지만, 마지막에 보낸 요청은 다시 보내야 합니다.
